# 编码与代码页（踩坑记录）

> 本文解释本仓库里**文件编码的硬性约定**，以及为什么必须这样。
> 起因是一次真实事故：把系统区域从日语改回简体中文后，**一键启动器直接报语法错误、桥接起不来**。

---

## 一、先搞懂：Windows 的「代码页」

Windows 有 Unicode 程序，也有大量**老式 ANSI 程序**（cmd、PowerShell 5.1、Dev-C++ 等）。
ANSI 程序**不带编码信息**，它按机器当前的「代码页」去猜字节是什么意思：

| 名字 | 用途 | 简体中文系统 | 日语系统 | 开了 UTF-8 Beta |
|---|---|---|---|---|
| **ACP** | 非 Unicode 程序（ANSI） | 936 (GBK) | 932 (Shift-JIS) | **65001 (UTF-8)** |
| **OEMCP** | 控制台、文件名 | 936 | 932 | 65001 |

同一串字节，在 ACP=936 和 ACP=65001 下会被解释成完全不同的文字——
**这就是所有乱码问题的总根源。**

查看当前值：

```powershell
Get-ItemProperty 'HKLM:\SYSTEM\CurrentControlSet\Control\Nls\CodePage' | Select ACP, OEMCP
chcp
```

## 二、事故复盘

### 症状

桌面「小鲸鱼QQ桥接」双击后，SnowLuma 起来了，但**桥接起不来**，端口 3100 一直是关的。
直接跑启动器，报一堆语法错误：

```
At D:\...\scripts\start-all.ps1:52 char:1
+ }
+ ~
Unexpected token '}' in expression or statement.
```

### 根因

`start-all.ps1` 存的是 **UTF-8 无 BOM**。而当时系统刚做了两件事：

```
系统区域: ja-JP → zh-CN
ACP:      65001 → 936        （关掉了「Beta: 使用 Unicode UTF-8」）
```

于是 PowerShell 5.1（ANSI 程序）改用 **GBK** 去解码这个 UTF-8 文件 →
本该是中文的地方变成了别的字符 → **把引号、括号的配对搞崩了** → 语法错误。

一句话：**文件编码和系统代码页对不上，脚本连解析都过不去。**

### 修复

给所有 `.ps1` 加上 **UTF-8 BOM**。带 BOM 时，PowerShell 会明确按 UTF-8 解码，
**不再看系统代码页**，于是换区、换代码页都不受影响。

## 三、本仓库的编码约定（改文件前先看这张表）

| 文件类型 | 必须的编码 | 为什么 |
|---|---|---|
| `*.ps1` | **UTF-8 with BOM** | 无 BOM 时按系统 ACP 解码；ACP 是 GBK 而文件是 UTF-8 → 中文串错乱，可能直接语法错误 |
| `*.bat` / `*.cmd` | **纯 ASCII**（不含任何中文） | cmd.exe 按 OEM 代码页解释；纯 ASCII 在哪个区域下都不会错 |
| `*.js` / `*.mjs` | UTF-8（BOM 可有可无） | Node.js 一律按 UTF-8 读，不看代码页 |
| `*.json`（含 `config.json`） | UTF-8 | 同上 |
| `*.md`（文档/角色卡/知识库） | UTF-8 | 同上 |
| 用户写的 C/C++ 源码 | 看目标 IDE（见第七节） | 老 IDE（Dev-C++）不吃「无 BOM 的 UTF-8」 |

> **一句话记忆**：**PowerShell 脚本要 BOM，批处理要纯英文，其它一律 UTF-8。**

## 四、怎么检查、怎么修

### 检查某个文件有没有 BOM

```powershell
$b = [System.IO.File]::ReadAllBytes('D:\肥鱼的工作区\qq-bridge\scripts\start-all.ps1')
if ($b[0] -eq 0xEF -and $b[1] -eq 0xBB -and $b[2] -eq 0xBF) { '有 BOM ✓' } else { '无 BOM ✗ 需要修' }
```

### 批量给 .ps1 补 BOM

```powershell
$utf8bom = New-Object System.Text.UTF8Encoding($true)   # $true = 带 BOM
Get-ChildItem 'D:\肥鱼的工作区\qq-bridge' -Recurse -Filter *.ps1 -File | ForEach-Object {
  $b = [System.IO.File]::ReadAllBytes($_.FullName)
  if (-not ($b.Length -ge 3 -and $b[0] -eq 0xEF)) {
    Copy-Item $_.FullName "$($_.FullName).bak-enc" -Force
    [System.IO.File]::WriteAllBytes($_.FullName, $utf8bom.GetPreamble() + $b)
    "已加 BOM: $($_.Name)"
  }
}
```

（前提：文件本身的内容确实是 UTF-8。如果它本来是 GBK，这样会把它弄坏——先确认再改。）

### 验证脚本语法有没有崩

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\start-all.ps1 -DryRun
```

`-DryRun` 只体检、不结束进程、不启动桥接，是安全的自检方式。

## 五、日志是 UTF-8 —— 读的时候要注意

`state\bridge.log`、`state\qq-activity.log` 都是 **UTF-8**，
而且日志时间戳是 **UTC**（比本地时间早 8 小时），行内**只有 `HH:mm:ss`、没有日期**。

在 ACP=936 的机器上用 `Get-Content` 直接读，会看到满屏乱码：

```
10:16:05 [bridge] [sticker] 宸插悓姝?QQ 鏀惰棌琛ㄦ儏 100 涓紙鏈湴搴?100 鏉★級   ← 乱码
```

正确读法（显式指定 UTF-8）：

```powershell
[System.IO.File]::ReadAllText('D:\肥鱼的工作区\qq-bridge\state\bridge.log', [System.Text.Encoding]::UTF8)
# 或
Get-Content .\state\bridge.log -Encoding UTF8
```

> 注意：**日志乱码 ≠ 程序出错**。先确认是不是自己读的方式不对，再去查 bug。

## 六、连带影响：命令行的中文显示

桥接的日志文件是 UTF-8，但 Node.js 往**控制台**输出时是直接写 UTF-8 字节，
而控制台按 OEM 代码页（936）解释 → 窗口里看到的中文会乱（**文件里是好的**）。

要在这个窗口里看正常中文，先切控制台代码页：

```bat
chcp 65001
node src\bridge.js
```

`start.bat` 里就带着这一句。

## 七、配套：Dev-C++ 与源码编码

同一台机器上，Dev-C++ 5.11 也吃这个亏，规则不同（**它靠 BOM 认 UTF-8**）：

| 系统状态 | Dev-C++ 里源码该存什么 |
|---|---|
| ACP = 65001（UTF-8） | **UTF-8 with BOM**（无 BOM 会被当成本地区域编码 → 乱码） |
| ACP = 936（简体中文） | **ANSI / GBK**（最稳；UTF-8 带 BOM 能显示，但 `printf` 输出会乱） |

配套的界面设置（`%APPDATA%\Dev-Cpp\devcpp.ini`）：

```ini
Language="Chinese.lng"          ; 语言文件要与当前代码页同编码（GBK 或 UTF-8）
InterfaceFont="Microsoft YaHei" ; 界面字体必须含中文字形
[Editor.Font]
Name="NSimSun"                  ; 等宽 + 简体中文字形
Charset=134                     ; GB2312_CHARSET，避免落到日文字形
```

> 语言文件 `Lang\Chinese.lng` 的编码**必须和系统代码页一致**：
> ACP=936 时要 GBK，ACP=65001 时要 UTF-8。不一致就会满屏乱码。

## 九、第二起事故：`Get-Content -Raw` 不等于 UTF-8

> 2026-09-19 深夜，为修蓝屏后的启动问题排查时撞上的。**同一个坑的第二种形态**：
> 上一次是"脚本文件本身没 BOM 被读成乱码"，这次是"脚本去读别的文件时没指定编码"。

### 症状

启动器里的这一句：

```powershell
$cfg = Get-Content (Join-Path $root 'config.json') -Raw | ConvertFrom-Json
```

稳定抛异常：

```
Invalid array passed in, ',' expected. (2070): {
  "dsh": {
    "baseUrl": "http://127.0.0.1:3080",
    ...
```

但同一个 `config.json` 用 node 解析完全正常 —— 说明文件本身没问题。

### 根因

**Windows PowerShell 5.1 的 `Get-Content` 不指定 `-Encoding` 时，按 ANSI 代码页解码。**
本机 ACP = 936（GBK），而 `config.json` 是 UTF-8 → 中文被解成乱码，
乱码字节里恰好出现了破坏 JSON 结构的字符（引号/转义）→ 解析直接失败。

后果非常隐蔽，值得记住这个链条：

```
try { ... } catch { }        ← 异常被吞掉，只在控制台留一行
   ↓
$cfg = $null
   ↓
拿不到 OneBot 的 accessToken → 请求 401
   ↓
健康检查判定"OneBot 无响应"
   ↓
把运行正常的 SnowLuma 当成"僵尸实例"杀掉重启 → 反复重启，永远登不上
```

也就是说：**一个编码问题伪装成了"网关卡死"。** 日志里只看到"OneBot 无响应"，
完全看不出是读配置失败。

### 修法（本仓库的硬规则）

凡是 PowerShell 读**文本 / JSON / 日志**，一律显式写编码：

```powershell
Get-Content $path -Raw -Encoding UTF8
[System.IO.File]::ReadAllText($path, [System.Text.Encoding]::UTF8)
```

读 `.lnk` 快捷方式用 COM，不要用文本方式读：

```powershell
$sh = New-Object -ComObject WScript.Shell
$sh.CreateShortcut($path).TargetPath
```

> `-Encoding UTF8` 读**带不带 BOM** 的 UTF-8 都能正确解码（这点和"写"不一样：
> `Set-Content -Encoding UTF8` 会写入 BOM）。所以第三节那张表管的是**写文件**，
> 这一节管的是**读文件** —— 两边都要遵守。
