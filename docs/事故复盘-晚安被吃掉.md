# 事故复盘：一句「晚安」是怎么被静默吃掉的

> 记录时间：2026-09-18 深夜
> 影响：主人发的一条私聊消息**没有被任何环节报错**，但机器人永远没看到它。
> 结论先说：不是模型「不想回」，也不是消息发送失败，而是**桥接把「已读」当成了「已处理」**。

---

## 1. 现象

2026-09-18 23:25–23:26（本地时间），主人连发三条：

| 时间 | 方向 | 内容 |
|---|---|---|
| 23:25:28 | 主人 → 她 | 宝宝，我准备睡觉了 |
| 23:25:32 | 主人 → 她 | 今天好累 |
| 23:25:59 | 她 → 主人 | 折腾一天了，快去睡 / 明天周六，能睡个懒觉 |
| **23:26:08** | **主人 → 她** | **晚安宝宝，爱你** |
| 23:39:21 | 她 → 主人 | （补发）刚才一直等你再说话呢 / ……晚安，也爱你 |

中间 13 分钟没有任何回复、没有任何报错。日志里连一行「异常」都没有。

## 3. 根因：两个洞叠在一起

### 洞 1：`qq_wait_for_messages` 看不见「等待开始之前」到的消息

等待接口的长轮询基线是**开始等待那一刻**的 `lastUnreadSeq`：

```js
const baseline = st.lastUnreadSeq || 0;      // 15:26:22 时 = 297
...
if (nowSeq - baseline >= minNew) { arrived = true; ... }   // 只有 >297 才算「新消息」
```

那句晚安（seq 297）在 15:26:08 就到了，比等待开始早 **14 秒**，于是它永远不可能作为
`newMessages` 出现。她等了整整 5 分钟，拿到的是 `timeout: true`——在她的视角里，
「主人没再说话，应该是睡了」。

> 这个设计本身是为了「只等新消息」，但它没考虑**手里还有没处理完的未读**这种情况。

### 洞 2：`qq_mark_read` 把「没看过」也一并清掉，而补发保险又完全信任这个结果

`mark_read` 原本无条件清空未读：

```js
const markedCount = st.unread.length;
st.unread = [];                    // ← 297 从来没进过她的上下文，却在这里消失
```

而 turn/end 时那道「繁忙期间补发」的保险，判定条件是「unread 里还有没有 seq ≥ 被暂存的那条」：

```js
const stillRelevant = stEnd.unread.some((m) => Number(m.seq) >= Number(item.seq));
if (stillRelevant) scheduleWakeV2(key, item.reason);
else log('繁忙期间唤醒 ... 已被当前回合处理，跳过补发');
```

unread 刚被清空 → `stillRelevant === false` → **保险判定「她已经处理过了」**，补发被跳过。
于是那条被正确暂存的唤醒，连带消息本身，一起消失了。

### 一句话总结

`qq_mark_read` 的真实语义是「**我看过这些，选择不回**」，但桥接拿它当
「**这个序号之前的都处理完了**」。两者在「回合进行中新到的消息」上不等价——
那正是她根本来不及看的消息。

---

## 4. 修法：把「看过」和「不回」彻底分开

新增一个会话级字段 **`deliveredSeq`**：她**真正看过**的最高消息序号。
只有桥接把消息**内容**交到她手上时才推进，具体三处：

| 推进点 | 位置 | 说明 |
|---|---|---|
| `qq_get_unread_messages` | `/api/socialV2/unread` | 返回给她的那些，最大 seq |
| `qq_get_recent_messages` | `/api/socialV2/recent` | 最近消息里别人发的最大 seq |
| `qq_wait_for_messages` | `/api/socialV2/wait` | 等待返回的 `newMessages` / 前置返回的未读 |

注意：**唤醒提示词不算**——唤醒 prompt 里只有「未读 N 条」和最近一条的前 30 个字预览，
不构成「看过」。

然后三处消费它：

**① `mark_read` 只清看过的，没看过的留着并明说**

```js
const delivered = Number(st.deliveredSeq) || 0;
const keptUnread = st.unread.filter((m) => m && Number(m.seq) > delivered);
const markedCount = st.unread.length - keptUnread.length;
st.unread = keptUnread;
```

返回里带上 `keptCount` 和一句 `note`（外加 `keptPreview`），告诉她「这些你还没看过，
先看了再决定要不要睡」。

**② 补发保险改用 `deliveredSeq` 判定**

```js
const stillRelevant = Number(item.seq) > deliveredNow
  || (Array.isArray(stEnd.unread) && stEnd.unread.some((m) => m && Number(m.seq) >= Number(item.seq)));
```

只要触发它的消息**她没看过**，就一定要补发——不再因为 `mark_read` 清空未读而误判。

**③ 等待工具先把「没看过的未读」交出来**

进入长轮询之前先检查：有 `seq > deliveredSeq` 的未读就**立刻返回**，不傻等：

```json
{ "ok": true, "arrived": true, "unseenUnread": true, "waitedMs": 0,
  "newMessages": [ ... ],
  "note": "先别等——你没看过的未读还有 N 条，它们比这次等待更早到，所以不会算作「等待期间的新消息」。" }
```

这一条是**本次事故的直接解药**：如果当时有它，她 0.04 秒就会拿到那句晚安。

## 6. 遗留与边界（诚实说明）

- **补发保险只覆盖「回合进行中被暂存」这一种情况**。如果一条消息压根没触发唤醒条件
  （概率没掷中、她正在潜水且没命中任何 trigger），它会安静地留在未读里，等她下次被
  唤醒时才会看到——这是设计如此（她主动选择潜水），但意味着「潜水期的消息不保证秒回」。
- **`deliveredSeq` 是单调递增的**。极端情况下（历史状态从没写过这个字段、值还是 0），
  第一次 `mark_read` 可能把本该保留的当作「没看过」；代价是多重启一次、多发一次唤醒，
  不会丢消息。
- **等待接口的前置返回不满足「沉睡前观察」**。故意如此：手里还有没看过的消息时，
  不该被允许直接潜水收尾。

## 7. 下次怎么排查同类问题

按这个顺序看，基本 2 分钟定位：

1. `state/bridge.log` 搜 `未读已读：N 条` —— 确认消息是在哪一步被标掉的
2. 搜 `暂存唤醒原因` / `跳过补发` —— 看保险有没有生效
3. `state/tool-calls.jsonl` —— 她那一轮到底调了哪些工具、什么时候调的（时间线最准）
4. `state/social-v2.json` 的 `unread` / `deliveredSeq` / `recentMessages` —— 当前余量
5. 控制台 `GET /api/socialV2/states?token=…` —— 所有会话的未读数一览

同一类事故**第二次**发生：`.ps1` 存成 UTF-8 **无 BOM**，PowerShell 5.1 在 ACP=936
（GBK）下按 GBK 解码 → 中文变乱码 → 引号/花括号配对全乱。

这次的教训是：**新建 `.ps1` 也要加 BOM**，不只是「修过的那些」。已用脚本对整个
工作区做了体检并补上（8 个脚本，补了 1 个），并确认所有 `.bat` 仍是纯 ASCII。
细节见 `docs/编码与代码页.md`。
